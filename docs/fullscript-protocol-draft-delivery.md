# Fullscript protocol draft delivery

Fullscript cart delivery is still incomplete. The existing protocol-cart API compiles a manifest and explicitly returns `not_implemented`; the new source does not change that contract, add a send button or create a real provider cart. Payload compilation, sandbox transport and an unreleased PostgreSQL delivery ledger are implemented. The current same-target authority adapter, actual provider response decoder, privacy lifecycle and runtime deployment remain required.

## Implemented payload and transport

`src/server/fullscript/protocol-draft.ts` accepts an existing parsed, compiled manifest and an explicit variant mapping set. It requires exact manifest identity/content binding, one mapping for every included line, no extra or duplicate line, an exact product identity, nonempty instructions and an explicit positive integer package quantity. Duplicate variants refuse instead of merging different phases or guessing quantities. Excluded lines are not in the provider payload. Catalog and mapping digests are binding inputs, not review evidence; the compiler explicitly returns `authorityVerified: false` and `providerCreated: false`.

The stable intent digest binds recipient, practitioner, manifest, catalog, mapping, variants, quantities and exact instructions. It forms the idempotency key. No purchase-link parsing, catalog search by product name, dose interpretation, package estimate, substituted product or automatic approval exists in this compiler.

`FullscriptApiClient.createSupplementDraft` is sandbox-only and requires the token's `clinic:write` scope before any request. It always specifies `state: draft`, `send_to_patient: false` and `skip_email_notification: true`. It sends supplement variants and explicit units only, retains the existing instructions as `dosage.additional_info`, and includes the same intent key in metadata, partner order identity and the idempotency header. No labs, activation, patient email, checkout or charge is introduced. `retrieveTreatmentPlan` and `findTreatmentPlanByMetadata` require `clinic:read` and provide explicit reconciliation reads; neither certifies a response as the correct cart.

The client snapshots configuration and scopes, refuses noncanonical API/OAuth origins, rejects redirects, bounds responses and makes one request per call. A failed or uncertain POST has no automatic retry. A repeated explicit call uses the same immutable input/key. The runtime passes the stored token's actual scopes; constructing a client without scopes grants no draft-write capability. The existing action route does not expose these new methods.

These behaviors follow the provider's [treatment-plan contract](https://fullscript.dev/technical-reference/treatment-plans), [idempotency rules](https://fullscript.dev/technical-reference/idempotency) and [metadata lookup](https://fullscript.dev/technical-reference/metadata). An omitted or null treatment-plan state defaults to active, so draft state must be explicit. The provider's advertised OpenAPI URL returned an HTML “Not supported” page during inspection; actual response-schema and sandbox acceptance remain unresolved, rather than being inferred from a fictional test response.

## Required runtime integration

The next increment must obtain the cart manifest, clinic, patient, practitioner, variant mappings, package quantities, current catalog/ingredient release and provider release from same-target server authority. Neither a client JSON mapping nor a matching digest is approval. Recheck access, consent, holds/exclusions, publication and supersession before admission and settlement. Preserve all excluded lines and mixed-provider lines in the owner-facing result rather than silently dropping them.

The unreleased ledger below implements immutable intent persistence, one writer admission, receipt checking and read-only lost-reply recovery. Integrate those operations with actual same-target authority and a verified provider response decoder; do not wire the fictional test dependencies into a route. A response URL alone is not success. Real provider idempotency and metadata behavior must pass sandbox acceptance before delivery is enabled.

Then implement the workforce/consumer scoped status and review controls, artifact-bound deployment, privacy/export/retention treatment for recipient-specific intents and receipts, and hosted sandbox acceptance including both race orders and lost replies. Patient delivery, activation, production use, commercial provider approval and covered agreements are separate gates. The legacy lab-checkout route is not reused as protocol-cart authority.

## Unreleased delivery ledger

`src/server/fullscript/draft-delivery.ts` persists a recipient-specific intent before any provider request. A transactional authority dependency resolves the manifest and recipient; caller JSON can select only a manifest and patient record, not supply mappings or approval. The dependency is required and has no installed production adapter. Its contract requires current same-target identity, connection, publication, catalog, ingredient, variant, quantity, consent, hold and provider-release checks. Hashes alone cannot satisfy it.

An admitted writer is recorded once and cannot be replaced, even after its 30-second deadline. A lost admission-commit reply produces no POST. A lost provider reply remains uncertain and offers metadata reads, never an automatic second POST or a new key. Empty, ambiguous or mismatched lookup results cannot certify absence. A known receipt surviving a lost database reply is read back rather than regenerated. Provider I/O runs outside database transactions.

Cancellation before admission prevents creation. Cancellation or authority loss after admission withholds any late receipt while retaining a verified external identifier for eventual reconciliation and cleanup. Read and settlement recheck current authority and the admitting practitioner's access. A verified receipt requires the exact patient, practitioner, metadata identity, draft state and complete recommendation set, including quantities and instructions, with no labs. Recommendation order can differ; content cannot. The observation contract is a normalized internal contract, not a guessed raw Fullscript schema. Actual response decoding remains unimplemented.

A reconciliation receipt does not prove an admitted process stopped: `writerPending` remains true until that process actually finishes. This ledger issues no deletion, recall or cleanup certificate. Its SQL denies API/public access and makes the recipient, input, writer identity and recorded receipt immutable. The dedicated no-login worker role has only select/insert/update. That internal role is not itself a per-owner RLS boundary; the mandatory transactional access adapter must be implemented, tested through the final runtime role and reviewed before any route is exposed.

`infra/aws-clinical-core/source-candidates/fullscript-draft-ledger.sql` is outside every released migration manifest. No released SQL, the 106-migration production identity or the qualification extension changed. This recipient-specific ledger must gain audit, export, retention, erasure/hold and provider-copy handling plus an artifact-bound upgrade before installation. It must not inherit the anonymous manifest's exclusion from patient privacy operations. No row or provider release was registered in AWS.

## Verification scope

`npm run test:fullscript-protocol-draft` covers the compiler, HTTP transport with fictional responses, existing cart contract and actual-SQL cart exclusions, plus the local SQL delivery ledger with fictional authority and normalized provider observations. It does not contact Fullscript or AWS, verify real OAuth scopes, qualify real provider deduplication, certify an actual provider response, deploy an endpoint or establish device acceptance. The original six commercial phases remain incomplete. PHI stays disabled, production activation blocked and paid mobile builds held.

At exact source `78653b46c845fed1e77e4927e2fcc5c9146aa10d`, the complete suite passed 377 files and 4,894 tests with 11 existing skips. Both hosted CI runs, `37960752446` and `37960744885`, completed successfully at that exact source. These results precede the delivery-ledger increment and do not qualify the provider or a deployment.

The final expanded gate passed 76 tests in six files with no skips, including 32 ledger tests. Typecheck and full lint passed. The production-schema gate passed 106 migrations with zero seeded rows; the new ledger remains outside that release. The ledger suite includes real PostgreSQL clock expiry, overlapping service instances, both cancellation orders, link replacement, admitting-actor revocation, lost admission and receipt commit replies, empty/ambiguous/mismatched recovery, exact recommendation matching and immutable SQL/role denials.

Earlier ledger attempts failed on an unavailable Zod method and test-harness TypeScript errors, then passed 29 tests after correction. A subsequent 75-test gate passed but its follow-up used a nonexistent script name; the final 76-test run used the correct production-schema gate and completed successfully. Local SQL tests do not prove AWS driver behavior, real OAuth scope, raw provider response compatibility, patient delivery or physical-device acceptance. The new increment's complete suite and hosted CI are tracked separately.
