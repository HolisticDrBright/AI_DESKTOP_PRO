# Fullscript protocol draft delivery

Fullscript cart delivery is still incomplete. The existing protocol-cart API compiles a manifest and explicitly returns `not_implemented`; the new source does not change that contract, add a send button or create a real provider cart. Payload compilation, sandbox transport, an unreleased PostgreSQL delivery ledger and a source-only same-target qualification authority adapter are implemented. Actual provider response decoding, credential binding, privacy lifecycle and runtime deployment remain required.

## Implemented payload and transport

`src/server/fullscript/protocol-draft.ts` accepts an existing parsed, compiled manifest and an explicit variant mapping set. It requires exact manifest identity/content binding, one mapping for every included line, no extra or duplicate line, an exact product identity, nonempty instructions and an explicit positive integer package quantity. Duplicate variants refuse instead of merging different phases or guessing quantities. Excluded lines are not in the provider payload. Catalog and mapping digests are binding inputs, not review evidence; the compiler explicitly returns `authorityVerified: false` and `providerCreated: false`.

The stable intent digest binds recipient, practitioner, manifest, catalog, mapping, variants, quantities and exact instructions. It forms the idempotency key. No purchase-link parsing, catalog search by product name, dose interpretation, package estimate, substituted product or automatic approval exists in this compiler.

`FullscriptApiClient.createSupplementDraft` is sandbox-only and requires the token's `clinic:write` scope before any request. It always specifies `state: draft`, `send_to_patient: false` and `skip_email_notification: true`. It sends supplement variants and explicit units only, retains the existing instructions as `dosage.additional_info`, and includes the same intent key in metadata, partner order identity and the idempotency header. No labs, activation, patient email, checkout or charge is introduced. `retrieveTreatmentPlan` and `findTreatmentPlanByMetadata` require `clinic:read` and provide explicit reconciliation reads; neither certifies a response as the correct cart.

The client snapshots configuration and scopes, refuses noncanonical API/OAuth origins, rejects redirects, bounds responses and makes one request per call. A failed or uncertain POST has no automatic retry. A repeated explicit call uses the same immutable input/key. The runtime passes the stored token's actual scopes; constructing a client without scopes grants no draft-write capability. The existing action route does not expose these new methods.

These behaviors follow the provider's [treatment-plan contract](https://fullscript.dev/technical-reference/treatment-plans), [idempotency rules](https://fullscript.dev/technical-reference/idempotency) and [metadata lookup](https://fullscript.dev/technical-reference/metadata). An omitted or null treatment-plan state defaults to active, so draft state must be explicit. The provider's advertised OpenAPI URL returned an HTML “Not supported” page during inspection; actual response-schema and sandbox acceptance remain unresolved, rather than being inferred from a fictional test response.

## Required runtime integration

The qualification adapter below obtains the cart manifest, clinic, patient, practitioner, variant mappings, package quantities, current catalog/ingredient release and provider release from the same database transaction. Neither a client JSON mapping nor a matching digest is approval. Runtime integration must independently bind the actual target and OAuth credential to the reviewed provider release, recheck authority before admission and settlement, and preserve all excluded lines and mixed-provider lines in the owner-facing result rather than silently dropping them.

The unreleased ledger below implements immutable intent persistence, one writer admission, receipt checking and read-only lost-reply recovery. The new authority port is tested against canonical SQL; integrate it with observed target/credential authority and a verified provider response decoder, not fictional test dependencies. A response URL alone is not success. Real provider idempotency and metadata behavior must pass sandbox acceptance before delivery is enabled.

Then implement the workforce/consumer scoped status and review controls, artifact-bound deployment, privacy/export/retention treatment for recipient-specific intents and receipts, and hosted sandbox acceptance including both race orders and lost replies. Patient delivery, activation, production use, commercial provider approval and covered agreements are separate gates. The legacy lab-checkout route is not reused as protocol-cart authority.

## Unreleased delivery ledger

`src/server/fullscript/draft-delivery.ts` persists a recipient-specific intent before any provider request. A transactional authority dependency resolves the manifest and recipient; caller JSON can select only a manifest and patient record, not supply mappings or approval. The dependency is required and has a source-only qualification adapter, not an installed production adapter. Its contract requires current same-target identity, connection, publication, catalog, ingredient, variant, quantity, consent, hold and provider-release checks. Hashes alone cannot satisfy it.

An admitted writer is recorded once and cannot be replaced, even after its 30-second deadline. A lost admission-commit reply produces no POST. A lost provider reply remains uncertain and offers metadata reads, never an automatic second POST or a new key. Empty, ambiguous or mismatched lookup results cannot certify absence. A known receipt surviving a lost database reply is read back rather than regenerated. Provider I/O runs outside database transactions.

Cancellation before admission prevents creation. Cancellation or authority loss after admission withholds any late receipt while retaining a verified external identifier for eventual reconciliation and cleanup. Read and settlement recheck current authority and the admitting practitioner's access. A verified receipt requires the exact patient, practitioner, metadata identity, draft state and complete recommendation set, including quantities and instructions, with no labs. Recommendation order can differ; content cannot. The observation contract is a normalized internal contract, not a guessed raw Fullscript schema. Actual response decoding remains unimplemented.

A reconciliation receipt does not prove an admitted process stopped: `writerPending` remains true until that process actually finishes. This ledger issues no deletion, recall or cleanup certificate. Its SQL denies API/public access and makes the recipient, input, writer identity and recorded receipt immutable. The dedicated no-login worker role has only select/insert/update. That internal role is not itself a per-owner RLS boundary; the mandatory transactional access adapter must be implemented, tested through the final runtime role and reviewed before any route is exposed.

`infra/aws-clinical-core/source-candidates/fullscript-draft-ledger.sql` is outside every released migration manifest. No released SQL, the 106-migration production identity or the qualification extension changed. This recipient-specific ledger must gain audit, export, retention, erasure/hold and provider-copy handling plus an artifact-bound upgrade before installation. It must not inherit the anonymous manifest's exclusion from patient privacy operations. No row or provider release was registered in AWS.

## Canonical cart source qualification port

The old cart compiler reads the legacy synthetic program tables. The unreleased `infra/aws-clinical-core/source-candidates/canonical-protocol-carts.sql` and `src/server/clinical-core/canonical-protocol-carts.ts` add a separate port for the actual canonical 106-migration schema. No public route selects it, no released migration identity changed, and it has not been installed in AWS. Its declared qualification configuration is not observed account, target, migration or MFA evidence; those must be independently checked by the future handler. Production execution is refused.

Compile requests name only a version. The database checks the current workforce identity and clinic membership, the active published program, exact approved content and an active approver. A transaction-level program lock serializes compiler and reader operations. Manifests freeze content, approval and current catalog digests; changed publication, approval, catalog evidence or destinations supersede the saved manifest without rewriting its lines. Explicit reads recheck authority; list results are inventory, not delivery authorization.

Products must resolve in the same database to a currently approved open supplement version and successful import. Its latest ingredient verification must be complete, source-verified `V`, tied to the exact product/version/content/label and backed by an active authorized reviewer and approved source references. An older approval cannot replace the newest withdrawal or malformed evidence. The program ingredient list must agree exactly, and its purchase URL must match a current approved destination. Program IDs, ingredient strings and purchase links are never independent catalog authority.

Every supplement line remains visible. Iron and reproductive exclusions persist; unreleased steps, unavailable catalog authority and missing approved destinations gain explicit exclusion reasons. No quantity is inferred and no provider cart is created. Private manifests and append-only, identifier-only audit events have no API/public table grants; the workforce function is the only API entry. Patient-specific ledger audit, privacy/export/retention and provider-copy handling are still separate unfinished work.

This cart port covers manifest source resolution only. The authority adapter below adds source resolution for the recipient-specific delivery ledger. Full delivery still requires observed runtime/credential bindings, actual provider response decoding, scoped review/status controls, a reviewed artifact-bound upgrade and real sandbox race/replay acceptance. The existing cart response remains `not_implemented`; no new purchase, activation, send or email operation is exposed.

The expanded local gate passed 99 tests in seven files, including 23 canonical-schema cases using the actual 106-migration artifact and the final API role with fictional review fixtures. Typecheck, focused lint and the 106-migration production gate passed with zero seeded rows. It covers approval/catalog changes, source-verification holds, restricted products, ingredient withdrawals, publication errors, cross-clinic and consumer denials, immutable manifests and audit history. Initial fixture attempts violated the real subject, foreign-key, membership-status and append-only catalog constraints; successor fixtures now preserve those protections. The tests also exposed a JSON operator-precedence defect and an unregistered generic audit action; the repaired candidate uses parenthesized comparisons and its own append-only audit table. No hosted or device result follows from these local tests.

At exact source `c121c74dde52e4383bfe66ac4c0d5eb08d15791e`, the complete suite finished successfully: 379 files, 4,949 passed and 11 existing skips. Both hosted CI runs, `37969526910` and `37969521148`, succeeded at that source. These results precede the authority adapter below and do not verify a provider or deployment.

## Canonical delivery authority qualification port

`source-candidates/fullscript-canonical-authority.sql` and `src/server/fullscript/canonical-draft-authority.ts` implement the required transaction-bound authority against the actual canonical schema. They remain outside the released 106/107 artifacts and every API route. Only the dedicated no-login worker can call the authority functions; API/public roles and the worker cannot read or mutate the authority, hold or external-consent tables directly. Deployment target and MFA verification, reviewed registration operators, and API wiring remain required.

Resolution requires a verified current patient connection, active consumer and workforce identities, clinic access, an active enrollment in the exact published version, current approved clinic-sharing copy and patient-app self grants for both programs and supplement protocols. It checks pending owner deletion and explicit delivery safety/privacy holds. The anonymous cart read rechecks the current publication, catalog, ingredient and destination authority. These are delivery holds, not a reinterpretation of legal holds that preserve records against erasure.

Immutable reviewed releases bind the sandbox provider and credential digest, patient/consumer/connection, practitioner, manifest, catalog and exact variant/package mappings. The latest revision must be current, not retired, and reviewed by an active authorized person; no older release is resurrected. Strict typed content rejects unknown fields, wrong origins, production environments, duplicated scopes, misbound identities, stale catalog/manifest hashes and invalid quantities. The payload compiler still guesses no dose or package quantity. A complete fingerprint binds the connection version, enrollment, clinic consent grants and every release to the durable intent. Changed authority refuses replay; it does not silently issue a new provider key.

External-provider consent is separate from consent to share a protocol with a clinic. Read, grant and withdrawal require the actual owner of the connection. The copy is tied to the current provider release, with its own UTF-8 digest and an immutable review. Grant binds the exact displayed release and revision; a new copy needs a fresh grant. Withdrawal remains available even after a release is retired. Every grant/withdrawal has an append-only identifier-only audit event. Historical receipt access remains with the original owner; replacing a link gives its new owner no access to the old receipt.

Expected authority denials return SQL `NULL`/`false`; the TypeScript adapter then refuses without aborting PostgreSQL's surrounding transaction. This allows the ledger to commit `withheld` and retain a verified late external identity after withdrawal, deletion fencing or access loss. A malformed latest catalog record or a missing release is not an exception that rolls back that settlement. The provider reply used in these tests is the normalized internal observation, not a real Fullscript response.

This port does not validate a real OAuth credential against the reviewed digest, contact Fullscript, activate patient delivery or authorize PHI. Recipient-specific intent/receipt audit, export, retention, erasure/hold and provider-copy lifecycle remain unfinished. The existing cart contract remains `not_implemented`. No release, consent, fixture or migration was registered in AWS.

The expanded local gate passed all 139 tests in eight files, with no skips, including 40 canonical authority cases against the actual 106 schema and worker/API roles. Typecheck, focused lint and the production-schema gate passed; the latter remains 106 migrations with zero seeded rows. Positive prepare/replay/send uses real database grants and releases but a fictional normalized provider. Negative cases cover retired latest releases, malformed or misbound reviewed content, source/catalog changes, exact external consent, withdrawal without an available copy, deletion fencing, delivery holds, inactive identities/reviewers, paused enrollment, both pre-admission and late-receipt authority loss, link replacement, original-owner isolation, strict requests and raw-role/immutability denials. These are local transactional tests, not AWS multi-session, provider or device acceptance.

The initial fixture used an invalid patient-key format. Later failures exposed test assumptions that an inactive owner could still read and that a revoked connection needed no timestamp. The fixtures and assertions were corrected without weakening identity or schema checks. The candidate also fixes an ambiguous scope comparison so programs and supplement-protocol consent are checked separately. Every production and qualification activation restriction remains unchanged; all six original commercial phases are still incomplete, PHI disabled and paid mobile builds held.
