# Production consumer email-verification drift — review only

The read-only checker `node scripts/check-aws-production-cognito-live.mjs --profile ai-production` pins AWS account `173535830222`, region `us-east-2`, stack `ai-longevity-production-clinical-foundation` and both `ConsumerUserPool` and `WorkforceUserPool` physical IDs. It requires an assumed-role session. It reads STS, CloudFormation and Cognito; it cannot change a pool or send email. CI runs only its credential-free tests via `test:aws-production-foundation`.

On 2026-10-17 the live checker exited 1 with `status: drift`: the deployed CloudFormation template declares `AutoVerifiedAttributes=["email"]` on **both** pools, but live `DescribeUserPool` reports it absent on both. The production SES domain is verified and sending access is enabled, but this does **not** prove Cognito sends a sign-up code. The fictional staging consumer pool has `AutoVerifiedAttributes=["email"]`, so its successful sign-up is not proof of the production configuration. A separate `GetUserPoolMfaConfig` read confirmed TOTP remains enabled in the production workforce and consumer pools; `DescribeUserPool.EnabledMfas=null` alone is not evidence of an MFA drift.

Read-only CloudTrail metadata showed direct `UpdateUserPool` calls on 2026-09-01 and 2026-10-14 that omitted `autoVerifiedAttributes`; the 2026-08-20 CloudFormation call included `email`. The likely reset mechanism is documented by [AWS UpdateUserPool](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_UpdateUserPool.html): unspecified settings revert to defaults. [AWS's sign-up guide](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-settings-admin-create-user-policy.html) ties `AutoVerifiedAttributes` to automatic confirmation delivery. This is a configuration-based risk, not a recorded failed production sign-up; no production test account was created.

The application's `src/server/clinical-core/aws-consumer-account-lambda.ts` calls Cognito `SignUpCommand` and `ResendConfirmationCodeCommand` rather than sending its own confirmation email, so the pool setting is relevant to that path. This is source evidence, not a live end-to-end result.

Before any repair, inventory the entire live pool against the approved template and all later intentional changes. A one-field `UpdateUserPool` is unsafe because it can reset unrelated settings; a no-op CloudFormation update is not proof that live drift is repaired. Prepare a separate preserving change/rollback review, obtain owner approval for the production write, and then use one controlled fictional inbox to test registration and reset without clinical data. Neither this checker nor the SES account status fills the V2 hosted/device acceptance cases or approves PHI.
