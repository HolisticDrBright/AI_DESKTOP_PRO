# Production governed-catalog schema bridge — release blocker

The workforce catalog API is a source candidate, not a deployable production catalog today. The production clinical database and the standalone governed-catalog package have different table and privilege contracts. A current clinic membership check alone does not bridge them.

## Reproduced source facts

- `infra/aws-clinical-core/catalog-migrations/` defines `clinical_reference.product_label_versions` and `clinical_reference.protocol_template_steps`. The existing `aws-governed-catalog-reader.ts` queries those tables directly under `clinical_core_api`.
- The assembled production clinical artifact defines `clinical_reference.product_label_verifications` and `clinical_reference.protocol_template_items` instead. It has no `product_label_versions` table and does not grant the API role direct `SELECT` on `catalog_product_versions`. It defines `clinical_core.get_product_catalog`, but the exact assembled artifact also does **not** grant `clinical_core_api` EXECUTE on that function. A named, reviewed projection function and precise grant are required; merely redirecting the API to this existing RPC is not a working fix.
- `catalog-production-schema-compatibility.database.test.ts` applies the real production migration artifact and pins those observations. The reader now checks the standalone schema shape before it can return even an empty production page; an incompatible target returns `catalog_unavailable`, not a false empty catalog.
- The unregistered `workforce-current-membership-context.sql` candidate can resolve an approved workforce subject and clinic in the clinical database. A separate catalog-only database cannot use that function without a reviewed, same-transaction authority design. No cross-database or stale-token shortcut is accepted.

## Required engineering before production catalog activation

1. Choose one authoritative production database and a single documented catalog contract. The recommended route is a reviewed production-clinical projection/RPC over the existing production catalog tables, with current membership and catalog data read in the same transaction. Grant EXECUTE on that exact function to `clinical_core_api`, revoke PUBLIC and leave table SELECT withheld. Do not grant broad direct table access merely to reuse the standalone reader.
2. Map exact reviewed label-version identity (`catalog_product_versions.id` and its source hash, rather than a generated label ID), strict source-verification evidence, product type/tier/restrictions, commercial offer authority, protocol items and dose provenance to a versioned API contract. `get_product_catalog` is a practitioner review summary, not this full contract. If the production schema cannot represent a field, add a preserving reviewed migration or version the API contract; do not fabricate an ID, label, dose or purchase eligibility.
3. Keep Core education-only offer suppression and all clinical holds independent of the catalog transport. Review the consumer route separately from the workforce route; a workforce membership decision must not be reused as consumer authority.
4. Add a real assembled-schema test with an approved fictional product and two clinics: active member succeeds, removed/suspended/cross-clinic member refuses, in-flight revocation is ordered correctly, and a missing or mismatched schema refuses before any empty success. Then run the same matrix against hosted fictional PostgreSQL, including the exact Lambda/database target.
5. Record the chosen artifact, schema migration hashes, API source hash, deployment target and rollback evidence. Keep the route disabled until those tests, reviewed source data and release approvals exist.

## Exact projection contract to implement

| Published field or rule | Authoritative production source and required refusal |
| --- | --- |
| Product ID, version and classification | Current `catalog_products.active_version` joined to that exact `catalog_product_versions` row. Both records must be approved, the import batch succeeded, environment `production-clinical`, `contains_phi=false`, and source references present. Preserve the database's `other` product type and `blocked` tier as **held** in a versioned contract; do not silently omit them or squeeze them into an eligible enum. |
| Label identity and source verification | The actual `catalog_product_versions.id` UUID and `label_sha256`, not a fabricated `lbl_` identifier. A free-text `product_label_verifications` row is not sufficient for AI recommendations or purchase; require a current, structurally valid source-`V` release proof bound to the product ID, version, content hash, label UUID and label hash. A later withdrawal or conflicting proof must withhold it. |
| Direct order and offers | Require the product and version to be eligible; exact active approved offer/version and successful batch; no restriction; an unambiguous destination; reviewed disclosure and current verification. Keep Core education-only responses free of destinations even if a workforce review can see the evidence. No URL in a program step is its own authority. |
| Protocol items and steps | Production stores `protocol_template_items` by `template_version_id`; standalone storage uses `(template_stable_id,template_version)`, and standalone `protocol_template_steps` has no production equivalent. Add reviewed production step storage or version the response with an explicit unsupported field; never invent phases, instructions or doses. |
| Workforce authority | Validate the selected clinic and signed workforce subject at the API, then call `set_current_workforce_context` and the projection in one short transaction. The projection checks current membership again through the existing production authority. Grant only EXECUTE on the exact projection to `clinical_core_api`; no direct table SELECT or cross-database stale-claim bridge. |
| Consumer authority | Design and test a separate owner-bound consumer projection. Do not borrow the workforce clinic session. Keep product suggestions, orders and directives withheld in education-only Core until clinical, legal, store and source-verification gates explicitly open. |

`get_product_catalog` currently reports a `verificationState` based on the presence of any label-verification row. That is a practitioner review summary, not proof that an ingredient-level source-`V` release exists. Its response and permissions cannot be adopted as the consumer purchase contract by renaming fields.

## Unregistered source-verification building block

`infra/aws-clinical-core/source-candidates/production-catalog-source-verification.sql` defines a private, non-API-callable helper against the assembled production schema. Its local database test requires a current approved product/version, a succeeded import, a complete exact source-`V` proof tied to the real version UUID and hashes, an active reviewer person, unique ingredient/source arrays, and no later withdrawal or malformed event. Missing, null, extra, or mistyped proof fields refuse. It grants neither the public nor the API role direct use. The existing write RPC checks catalog membership when it records a verification, but this helper cannot independently establish historical reviewer authority from that row. It also does **not** establish that a reviewer actually checked the label or sources, nor that an ingredient list matches a particular program step; those require reviewed evidence and a separate projection/release decision.

The helper has not been registered as a migration, deployed, called by the runtime, or approved for patient-facing recommendations. A usable workforce runtime bridge, a separate consumer projection and owner authority, release data, hosted revocation/race tests, and separate commercial/clinical approvals remain open.

An additional unregistered `production-catalog-reference-projection.sql` candidate builds a **workforce-only reference page** over the assembled production tables, after the current-membership context and private verification helper are installed. It keyset-pages exact approved current versions and successful imports, preserves `other`/`blocked` classifications and the real label UUID/hash, reports whether the strict source proof is present, and exposes no commercial destination. Its local database suite covers two clinics, removal/suspension, pagination, failed imports and least-privilege grants. This is not the existing `governed-catalog-api/1` response: the runtime has not been switched to `production-catalog-reference/1`, and the old reader still refuses the incompatible production schema. Program-step doses, label ingredient matching, offers, consumer owner authority and clinical release are not inferred by this reference page. An approved runtime adapter and hosted matrix are required before it is usable.

This note is not permission to apply SQL, enable commerce, deploy a catalog route, process PHI or mark any original readiness phase complete.
