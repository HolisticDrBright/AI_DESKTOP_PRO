# BLOCKED EMR note-save settlement candidate

This branch contains a source-only, unregistered SQL candidate, the gated API/adapter path, and a composer settlement flow. The new database RPCs remain **off by default** behind `CLINICAL_EMR_SAVE_RECEIPT_ENABLED`; the SQL has **not** been applied to AWS or approved for PHI. Do not enable the flag or register the candidate without the remaining work below.

Base source commit: `e45b60cf0ae8ceeffccd839a43e5955e0cea8d46`. Candidate file SHA-256 over its current bytes: `68cdc0e1c5738be53083ba07b9a2d9d8f8c7e26bd57cf57033bf9e86d55d7cd2`. This digest is **not** a registered production migration identity.

## Why it exists

Desktop CI run `38633207512` failed its first browser attempt after a conflict: the final save request had no observed response, and the composer remained on `Saving…`. The rerun passed, but a lost response after a first draft creation can make a blind retry create a second draft. The current composer has no request deadline, durable write identity or explicit unconfirmed state.

## What this candidate proves locally

- A UUID request ID and a fingerprint of the exact save inputs are recorded in `clinical_private.note_save_receipts` in the same transaction as the clinical draft/version/audit event.
- Repeating the same save returns the first receipt without another draft or version. Changing the payload under the same ID is refused. A failed first transaction has no receipt and can be retried safely with the same ID.
- A scoped receipt query returns `unconfirmed` or a saved note/version; it does not claim an absent receipt proves failure. A different practitioner or clinic cannot read another actor's receipt. The API role has no direct table access.
- `npx vitest run src/server/clinical-core/emr-note-save-settlement.database.test.ts`: 6/6 passed on the complete production migration artifact.
- The dispatcher and adapter now validate and forward a stable UUID request ID to the new RPC only when the flag is enabled. A first-create request without an ID is refused under the flag; existing-note legacy saves remain available for old clients. The receipt read is scoped by encounter, organization and actor. The flag defaults off.
- The Desktop compatibility manifest names both RPCs as **blocked candidates**, pinned to the candidate's exact SHA-256 and explicit feature flag. The compatibility checker rejects a missing/changed candidate, a production-native claim, an ungated adapter/dispatcher or an unreviewed operation. The production operation manifest is unchanged; neither RPC is listed as active. The source-derived port inventory was refreshed and still reports 0 enabled operations.
- The composer bounds the POST and receipt/readback calls, serializes saves, tracks an explicit unconfirmed state, uses the same request ID for an explicit retry, and does not show Saved after a lost reply until the receipt and authoritative content/version agree. Review and signing are disabled during uncertainty. A sign-in or organization change clears the old note view and fences late responses.
- Focused adapter, dispatcher and database tests: 66 passed. Typecheck, focused lint, the clinical production build and the strict client-bundle scan passed. Six local fictional-data browser tests passed across four independent runs: committed/lost response, unconfirmed save with no blind retry or signing, a request held unanswered through the actual 12-second deadline, explicit same-ID first-create retry, the existing reload/sign/addendum/audit journey, and the existing two-tab conflict recovery. These browser tests intercept failure responses; they do **not** prove hosted PostgreSQL contention.
- The first SQL-only push (`99941f8`) had a CI failure in the pre-existing conflict browser test: its conflict panel was not observed within the unchanged 10-second assertion; 102 other tests in that shard passed. That test passed unchanged on this working tree locally. Exact-head CI [38646177207](https://github.com/HolisticDrBright/AI_DESKTOP_PRO/actions/runs/38646177207) on source commit `55197bfd` later passed all 11 jobs. Do not reclassify the earlier failed run as a pass.
- The full local unit run after the first integration push reported 8,696 passed and two failures. One was the operation inventory hash, generated before the blocked-candidate manifest was updated; it was regenerated and its reporting test now passes. The other was a Windows-only development-browser harness bug: the allowlisted renderer path used `/` while Node's stack uses `\`; the hook remained enabled. Normalizing separators fixed it, and all 26 tests across those two previously failing files pass in isolation. Exact-head CI confirmed the combined tree; the old local run remains recorded as failed.
