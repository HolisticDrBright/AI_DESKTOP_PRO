# Workforce token binding candidate — source only (14 October 2026)

This is an **inactive design candidate**, not practitioner registration or PHI activation. `src/server/clinical-core/aws-workforce-token-binding.ts` has no Lambda entrypoint, deployment template, runtime database adapter, or Cognito trigger. An unregistered SQL lookup candidate exists at `infra/aws-clinical-core/source-candidates/workforce-token-binding-lookup.sql`; it is not in a migration assembly and has never been applied to AWS. Its real release constant is `blocked`; the approved-release cases exist only in unit tests. No production pool, user, token or patient record was changed by this candidate.

## Why this candidate exists

The public workforce app client now permits only `email` writes. Existing Cognito schema attributes `person_id`, `organization_id` and `production_bound` are immutable. An applicant must not supply clinical claims at sign-up, yet the existing clinical services expect them in an ID token. [AWS permits a pre-token-generation trigger to add, replace or suppress `custom:` ID-token attributes](https://docs.aws.amazon.com/cognito/latest/developerguide/user-pool-lambda-pre-token-generation.html). The observed workforce pool is on the Plus tier and has no pre-token trigger today. This candidate explores a trusted, database-derived claim at token issuance without making a public applicant an authority for it.

The pure handler pins the pool, client, region, subject and supported V1 trigger source. It strips all three clinical claims for a blocked release, unverified email, absent approval, inactive identity/person/clinic/membership, multiple approved memberships or a missing production binding. It rejects a cross-subject result, malformed approved IDs and database lookup outage. It can add the three claims only for one current, active, database-approved membership under a separately reviewed activation mode. It does not change groups or accept client-supplied organization attributes.

The source now distinguishes two **test-only simulated modes** while the real release remains `blocked`. `qualification` requires `PhiAllowed=false`, the observed synthetic workforce pool/client in account `588966314750`, a bounded exact list of one to four designated fictional Cognito subjects and a review-evidence digest. An unlisted subject receives no clinical claims and triggers no database lookup. `approved` is pinned to the observed production pool/client, requires `PhiAllowed=true` and its separate evidence, and refuses any qualification account or allowlist fields. The issuer and app-client checks in the eventual API remain mandatory; a synthetic token must never be accepted by the production clinical API. Neither simulated mode is wired to Lambda or Cognito.

## What must exist before any hosted trial

1. Review and register the unregistered private lookup candidate, then implement a runtime adapter keyed by the immutable Cognito `sub`. The candidate filters to the workforce pool and current production-bound identity, person, organization and membership; it refuses zero or multiple active clinics. It grants its function only to a dedicated non-login, non-inheriting `clinical_token_binding` role, not the general API role. The local database test applies the full production artifact plus the candidate, verifies the role separation and denial cases, and caught a PostgreSQL `min(uuid)` mistake before it could be shipped. A reviewed execution identity, exact database privileges, hosted PostgreSQL proof and audit/monitoring are still missing. Do not trust requested clinic, email or Cognito custom attributes.
2. An audited onboarding workflow: verified account requests to join an existing clinic **or** proposes a new clinic, an existing clinic administrator or platform operator approves the appropriate request, and revocation is immediate at the clinical database boundary. Registration and confirmation themselves grant no membership. Avoid exposing a clinic directory or request status to unrelated applicants.
3. A reviewed multi-clinic selection contract. This candidate intentionally strips claims when more than one approved membership exists; it must not be activated for clinicians with multiple clinics until per-session selection, cross-device behavior and stale-token handling are designed and tested. A global mutable “current clinic” is not enough to prove simultaneous-device isolation.
4. A complete inventory of workforce consumers of `custom:person_id`, `custom:organization_id` and `custom:production_bound`, including the identity API and other Lambdas. Each must still check current database membership on every patient-data operation. Token refresh alone is not a revocation guarantee.
5. Shadow comparison and backfill for **existing** practitioners before attaching a trigger to the live pool. A missing binding or database outage could otherwise block sign-in or withhold their claims. Include real PostgreSQL transaction/revocation races, Cognito signup/confirmation/MFA/refresh, account-switch and two-device tests with fictional identities in qualification. Observe trigger latency and an outage drill.
6. A reviewed infrastructure candidate: exact Cognito pool trigger config, Lambda invoke permission, narrowly scoped database and secret grants, encryption and log redaction, alarms, rollback and change set. Do not use a sparse `UpdateUserPool` call. Keep `PhiAllowed=false` and activation blocked until separate human/provider/security gates are satisfied.

The pure source tests are **25 passing local cases** and the unregistered SQL candidate has **3 passing embedded-database cases** against the assembled production schema. They do not prove Cognito accepts the overrides, hosted PostgreSQL privileges, old-token fencing, or any live app flow. The separately disabled registration route in `docs/workforce-self-signup-blocker-2026-10-14.md` remains disabled.
